# YAMCS compared with the Rust GDS design

Sources read: YAMCS `master` at commit `4af5abd` (2026-11-18), source and `docs/server-manual`; `fprime-community/fprime-yamcs` at `f6f0e19`; `the design document as it was before these ideas were adopted`.
Paths below are relative to the YAMCS repository unless prefixed `fprime-yamcs:`. `L` means line numbers.
Nothing was run; every YAMCS claim comes from reading. Items marked **(inferred)** are my reasoning, not something I read.
Not read: the Python client source (separate repository), YAMCS security, the "Yamcs Gateway" mentioned in passing in `docs/server-manual/processors/command-processing.rst` L107.

Short version: YAMCS agrees with the user that framing belongs inside the server process, in front of routing. Our draft already does this and separates transport from framing more cleanly than YAMCS does. YAMCS's routing is data-driven (named streams plus the Mission Database), and the `fprime-yamcs` integration shows that this model fits F Prime poorly. Six small ideas are worth taking; the large ones are not.

## 2. Answers to the three points

### 2.1 Where should framing sit relative to adapter and router?

**YAMCS:** inside the server process, as part of the link, before data reaches streams and the processor. Packet splitting, frame decoding, virtual channel separation and the checksum/time preprocessor all run in the link (`general/architecture.rst` L32-34, L43). This is the arrangement the user asked for, not the Python GDS arrangement.

One weakness in YAMCS: transport and framing are tied together by class inheritance, so each combination needs its own class. There is a UDP frame link and no TCP or serial frame link (`links/ccsds-frame-processing.rst` L37). `fprime-yamcs` works around this by running the Python `fprime-comm-bridge` as a second process whose only framing job is to cut the TCP byte stream into whole frames and send one frame per UDP datagram (`fprime-yamcs:README.md` L31, L73-77). So the F Prime-on-YAMCS setup today has exactly the split the user dislikes, for a reason that is an accident of YAMCS's class design.

**Recommendation:** keep draft 5 as is on placement. Framing layers are plugins, run in the GDS process, and are called by the core between the adapter and the router (4.1 diagram, 4.3). Keep `Adapter` and `FramingLayer` as two separate extension points; this is better than YAMCS because any adapter works with any profile without a new class. Two small additions come from YAMCS (ideas 3 and 6 in section 3).

### 2.2 Should the adapter be able to run in its own process?

**YAMCS:** a link is always a class inside the server (`links/index.rst` L28-29). To put the transport elsewhere, YAMCS puts a network protocol in between and lets another program hold the hardware: UDP datagrams from any sender, the Space Link Extension plugin for ground stations (`general/architecture.rst` L30), another YAMCS through the cascading link (`links/yamcs-cascading.rst` L4-11), or stream replication (`services/instance/replication-master.rst` L5). There is no "remote link" plugin protocol.

**Recommendation:** in-process by default, and no new mechanism for the out-of-process case. The draft already has the two parts needed: `fgds comm-bridge` forwards between two adapters "with or without framing" (CLI-4), and the GDS has TCP and UDP adapters. A serial adapter on a lab machine is then `fgds comm-bridge --comm uart ... --to tcp-server` there, and `--comm tcp-client` on the GDS, with framing still done in the GDS. Reason: this gives the user's "maybe in its own process" without a second plugin interface, a serialization format or a supervisor for remote plugins to maintain. The cost to accept: the GDS sees the bridge, not the far hardware, so "link connected" means "bridge connected" **(inferred;** `fprime-yamcs` has the same limit**)**. Draft change: idea 2.

### 2.3 Should the router be a plugin, or is decoder registration enough?

**YAMCS:** routing is not one replaceable component; it is data. Links name their output stream in YAML, Stream SQL can filter and copy between streams, and the Mission Database decides which container definition applies to a packet (table row 2). A project changes routing by editing YAML, SQL and the XTCE dictionary, and can add a service that reads a stream directly.

Evidence on how well that fits F Prime: `fprime-yamcs` could not express F Prime events or the packed telemetry-channel packet in the Mission Database. It runs two extra supervised programs, one decoding events and one splitting channel packets and re-injecting each record through an extra UDP link, plus a custom Java service reading the stream for file packets (`fprime-yamcs:src/fprime_yamcs/yamcs/src/main/yamcs/etc/yamcs.fprime-project.yaml` L33-60, L78-82; `fprime-yamcs:README.md` L45-69). A general data-driven router did not remove the need for F Prime-specific code; it moved it into side processes.

**Recommendation:** decoder registration is enough; do not make the router a plugin and do not add a routing language. Reasons:
- F Prime has one routing key (the packet type) with a handful of values. A table from packet type to decoder is the whole router.
- The draft already has the escape hatches a project needs: register a `Decoder` for a new packet type, `override_decoder` for an existing one, or write a `Handler` that subscribes to `gds.unknown_packet` or to any kind's records (which carry `raw`) to do extra processing. That last one is the equivalent of a YAMCS service reading a stream.
- A project with a different packet header replaces a framing layer so packets arrive in the expected form (4.9). This is the same role as YAMCS's preprocessor.
- A plugin router would put ordering, error containment and "unknown packet" accounting (LNK-8, LNK-12) in project code, which is what 4.9 keeps in the core.

The one thing worth borrowing from the YAMCS model is idea 6 (packet metadata from framing), so that a future second routing key does not need a router change.

## 3. YAMCS ideas worth adopting, ranked

Ranked by benefit divided by maintenance cost.

**1. Dry run for commands.**
- Benefit: validate and encode a command and get the bytes back without sending. Useful for the Commanding tab (check before send), sequence tooling and tests. YAMCS: `dry_run` (`processors/command-processing.rst` L77).
- Cost: very low. The encoder already returns bytes or a validation error; this is one flag that stops before the guards and the write.
- Draft change: 4.7, row `POST /api/v1/commands`: add "`?dry_run=true` validates and encodes, returns the packet bytes, sends nothing and records nothing; viewer role is not enough". 4.5: add one `alt dry run` branch after "encode and validate". Add requirement LNK-19 in 3.2.

**2. State that a remote adapter is `comm-bridge` plus a network adapter.**
- Benefit: answers "adapter in its own process or not" with no new code, and removes an apparent contradiction between the non-goal and CLI-4.
- Cost: none in code; one integration test (bridge without framing in front of the GDS).
- Draft change: section 2, replace the third non-goal with "A dedicated protocol for running an adapter or framing outside the GDS process. An adapter can run in another process or on another machine by running `fgds comm-bridge` there without framing and pointing the GDS's TCP or UDP adapter at it; framing always runs in the GDS process. The GDS then reports the state of its connection to the bridge, not of the far link." Section 7, decision 5: same wording. CLI-4 verification: add "IT with the GDS behind a bridge".

**3. Tell the framing layers whether the transport keeps message boundaries.**
- Benefit: YAMCS treats UDP as "one datagram is one packet or frame" and uses a packet splitter only on byte streams (`links/packet-input-stream/index.rst` L11; `UdpTmFrameLink.java` L99). In the draft, `LinkReader::read` appends to one buffer, so a deframer cannot tell a datagram from a stream chunk. With boundaries known, a framing layer can resynchronize on every datagram after a bad one instead of scanning, and fixed-size frames over UDP need no configured length **(inferred)**.
- Cost: low. One boolean and one rule in the core read loop.
- Draft change: 4.3, `PeerInfo`: add field `message_boundaries: bool` (true for UDP). After the trait block add: "When `message_boundaries` is true the core passes each read to the deframer as one complete unit and the deframer drops, as `Discarded`, whatever is left of that unit; when false the deframer sees a continuous byte stream." `FramingLayer::deframer` gets `&PeerInfo` as a second argument.

**4. Operator can disable and re-enable the link.**
- Benefit: release a serial port or stop all sending without stopping the GDS and losing the session. YAMCS links have `enable`/`disable` and `enabledAtStartup` (`yamcs-core/.../tctm/Link.java` L60-74; `links/index.rst` L6, L31-34).
- Cost: low. The adapter task already has connect, retry and disconnect; this adds a fourth state and one route. One more thing to show in the status bar.
- Draft change: 3.2, new LNK-20: "An operator shall be able to disable the link (the adapter is closed and not retried; sends are rejected as under LNK-11) and enable it again, through the API and UI." 4.7: add `POST /api/v1/link {enabled}` (operator). 4.4 table, "Link lost or absent" row: add state `disabled`.

**5. Keep the command record open to later stages.**
- Benefit: YAMCS writes each stage (queued, released, sent, verified) onto one command-history entry (`data-management/archive/command-history.rst` L34-43), so the UI and tests can show "sent" and later "completed on board" as one item. The draft's `entity` field already supports "latest record per entity is the current state"; using it for commands costs nothing now and avoids a record-format change later.
- Cost: low now (one field). The verifier itself (matching F Prime's command-completed events to a sent command) is medium and should be a later, optional handler in the `commands` plugin; whether F Prime's completion events identify a single sent command unambiguously is **not verified**.
- Draft change: 4.2, in the paragraph on features that hold state, add "sent commands" to the list and state: "`fprime.command` sets `entity` to a per-send identifier; `outcome` is one of `rejected`, `failed`, `sent`, and may later be extended with `completed` and `error` by a handler that matches flight software command events." 4.5 diagram: `fprime.command {entity, outcome: ...}`.

**6. Let framing attach a small metadata map to each packet.** (Optional; lowest rank.)
- Benefit: YAMCS frame handling knows the virtual channel, and the preprocessor produces sequence count and validity before the dictionary is involved (`links/packet-preprocessor/index.rst` L6-13). In the draft `Deframed::Packet(Bytes)` drops everything the framing layers learned (virtual channel, application identifier, frame counter). Keeping it lets a decoder or handler report frame gaps or treat a second virtual channel differently, without a router change.
- Cost: low, but it widens a public type that is hard to change after M6. Only worth it if CCSDS use beyond the stock profile is expected.
- Draft change: 4.3: `Deframed::Packet { bytes: Bytes, meta: PacketMeta }` with `PacketMeta { vc: Option<u8>, apid: Option<u16>, seq_count: Option<u32> }`; `Decoder::decode` receives `&PacketMeta`. 4.9, last row: add "the router still keys on the packet type only".

## 4. YAMCS ideas recommended NOT to adopt

| Idea | Why not |
|---|---|
| Streams and Stream SQL as the routing layer (`data-management/streams.rst`) | A query language, its parser and its documentation are a permanent maintenance cost. Our records plus `Handler` subscriptions with structured filters cover the same uses, and SCR-6 forbids evaluating client-supplied expressions. |
| Dictionary-driven packet identification (XTCE container inheritance) | F Prime packets are identified by one field. `fprime-yamcs` shows the general model still needed three pieces of F Prime-specific code outside it (section 2.3). |
| Classes named in YAML and loaded from `lib/ext` at run time | Already a non-goal (no dynamic loading). YAMCS pays for it with untyped configuration maps and errors found at start instead of at build. Our compile-time registry plus run-time selection (CUS-9) gives the operator the same choices among compiled-in parts. |
| Command queues with a "blocked" state that holds commands for release (`tc/index.rst` L30-79) | Contradicts decision 4 and LNK-11 (never hold a command). A hazardous-command check fits `UplinkGuard` with a confirm flag in the request. YAMCS itself does not enforce significance in the server (`tc/index.rst` L18). |
| Transmission constraints and telemetry-based verifiers defined in the dictionary (`command-processing.rst` L93-127) | Needs a rule language in the dictionary that F Prime's JSON dictionary does not have. If wanted, completion tracking is a handler (idea 5), and pre-send rules are guards. |
| COP-1 retransmission, virtual channel multiplexing with priorities, Reed-Solomon, encryption associations in the core (`links/ccsds-frame-processing.rst`) | Large, standards-heavy code. A project that needs one writes a framing layer; the ordered-profile design already allows it. One caution: a linear chain of layers cannot send two virtual channels to two different consumers; idea 6 is the cheap hedge. |
| Several links per instance, link fail-over for commands, several instances per server (`LinkManager.java` L503-545; `general/architecture.rst` L13-18) | Non-goal "one link per GDS". Each multiplies status, routing and test cases. |
| One table per data type and a separate derived Parameter Archive | Our single table with `kind` is what lets a project add a record kind without touching storage (CUS-7). A column archive is a second storage engine to maintain. If long-range charts become slow, add an index or a derived table inside the SQLite plugin; keep the YAMCS principle that derived data is rebuildable from stored records, which the draft already satisfies by keeping `raw`. |
| Spacecraft generation time as the primary key, with duplicate rejection (`archive/telemetry-packets.rst`) | It exists to merge recorded data dumped later with realtime data. It makes ordering depend on a flight clock that F Prime boards often do not have set, which the YAMCS docs themselves call a difficulty (`links/packet-preprocessor/index.rst` L15-17). Our ground sequence number gives the gap-free replay-then-live that the test API needs. |
| Replay as a second processor with speed control | Useful for operations review, not for a development GDS. `--read-only` plus history queries cover browsing old runs. |
| Stream replication and cascading servers | Multi-site operations feature; out of scope and a second network protocol. |
| Two wire formats (JSON and Protocol Buffers) on the API (`docs/http-api/websocket.rst` L16-29) | Doubles the client contract. JSON only. |
| Static-folder web extensions (`WebPlugin.addExtension`, experimental) | The draft's tab contract with a `gds` object is already stricter and is what CUS-5 needs. |

## 5. What the comparison confirms in draft 5

- Framing in the core process before routing: same as YAMCS.
- Rejecting a command when the link is down rather than holding it: same as YAMCS's default behaviour (`LinkManager.java` L535-543).
- Recording undecodable input instead of dropping it: YAMCS has the same with `invalidPackets: DIVERT` and `badFrameStream` (`links/index.rst` L48-58; `ccsds-frame-processing.rst` L144).
- A supervised child process for the flight software: YAMCS `ProcessRunner`.
- Per-link status and counters visible to operators: YAMCS `Link` interface (`Link.java` L41, L89-93).
